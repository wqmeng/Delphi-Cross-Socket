# #199 修改前后性能对比（2026-10-28）

结论：本机测试中，#199 新实现的常见短头/10 字段解析和发送编码成本明显增加，FPC 字段解析回退最大。端到端损失小于局部函数耗时增幅，且强烈依赖内存管理器；默认 RTL 组观察到下降但噪声较大，FastMM5 组只呈小幅下降。新增原始值使存活对象更大，不能把累计分配字节减少误当成驻留内存减少。

## 版本和条件

- Before：`566187c283ebb3105e57ac9c8dd148a952b014d1`，即 #199 提交的父版本。After：`5e63745` 的实现加本轮之前已完成的注释补齐。两边均有此前 GetString 优化和 DateTime 修复。
- 冻结 Net/Utils/DelphiToFPC/zLib.inc 共 68 个源文件。除 #199 的五个生产文件外，MurmurHash 仅有 CRLF/LF 差异，规范化换行后完全相同。没有覆盖生产文件。
- Windows 10 19044，32 个逻辑处理器，AMD64 Family 25 Model 33 Stepping 2；系统 ANSI 代码页 936。编译器使用本机 Delphi D13.1 和 FPC 3.3.1 工具链，三目标各自 A/B 使用完全相同的 Release 开关。
- 微基准使用默认内存管理器，线程亲和掩码 4（逻辑 CPU 2），同进程预热，再交替 A/B 七轮。计时循环按较快端校准到约 250 ms；分配统计另跑，不把计数包装器混入普通计时。
- 端到端使用正式 HttpServer 示例的隔离副本，统一 HTTP、127.0.0.1:18080、65 个默认 I/O 线程、128 并发、210 字节响应（正文 78 字节）。默认 RTL / FastMM5 各自 A/A 三轮、A/B 五轮；ab 预热 2 万后计时 10 万请求，Bombardier 每次 10 秒。保持头体分离及 SOMAXCONN。

## 分配与对象占用

分配计数来自 RTL 内存管理器入口，累计申请字节包含每次申请/扩容请求，不是峰值、进程工作集或仍存活的内存。以下为复用请求对象解析同一 10 字段头的每次操作。

| 编译器 | 分配调用次数 前→后 | 累计申请字节 前→后 |
| --- | ---: | ---: |
| Delphi Win64 | 41 → 51 | 5407 → 4498 |
| Delphi Win32 | 41 → 51 | 5003 → 3818 |
| FPC Win64 | 51 → 61 | 6024 → 5403 |

另保留 5000 个对象，用 GetHeapStatus.TotalAllocated 的增量/对象衡量实际存活数据，三轮取中位数。输入、对象指针数组及共享 Server/Connection 不计入增量；受各 RTL 分配块舍入影响，只比较同编译器前后。释放后差值为 0 或至多 -24 字节的微小背景变动。

| 编译器 | 对象 | 修改前 B/对象 | 修改后 B/对象 | 变化 |
| --- | --- | ---: | ---: | ---: |
| Delphi Win64 | Header | 2112 | 3360 | +59.1% |
| Delphi Win64 | 请求对象（含 Header/快照等） | 4984 | 5536 | +11.1% |
| Delphi Win32 | Header | 1776 | 2696 | +51.8% |
| Delphi Win32 | 请求对象（含 Header/快照等） | 4148 | 4360 | +5.1% |
| FPC Win64 | Header | 2240 | 3216 | +43.6% |
| FPC Win64 | 请求对象（含 Header/快照等） | 5040 | 5408 | +7.3% |

记录本身大小：Delphi/FPC Win64 为 16→32 字节，Delphi Win32 为 8→16 字节；10 个字段的 RawValue 有效载荷合计 506 字节。Header 的额外持有成本明显，但原始请求快照从 UTF-16 字符串改成字节数组抵消了一部分，所以完整请求对象的增长为约 5%～11%，不是翻倍。移除整块头部文本等临时转换使累计申请字节减少，两项指标并不矛盾。

## 真实 HTTP 吞吐（Delphi Win64）

正式 128 并发样本（含 A/A）合计 Bombardier 成功请求 19,805,358 次、ab 计时请求 3,200,000 次；所有样本零错误、零非预期状态码，响应大小一致。下面取 A/B 五轮各自中位数。

| 内存管理器 | 指标 | 修改前 | 修改后 | 变化 |
| --- | --- | ---: | ---: | ---: |
| 默认 RTL | Bombardier 成功请求/秒 | 26,270.799 | 24,235.915 | -7.75% |
| 默认 RTL | ab 请求/秒 | 27,689.510 | 26,067.120 | -5.86% |
| 默认 RTL | Bombardier P99 ms | 46.873 | 55.660 | +18.75% |
| 默认 RTL | 服务端 CPU μs/成功请求 | 57.668 | 55.650 | -3.50% |
| FastMM5 | Bombardier 成功请求/秒 | 98,754.757 | 97,216.063 | -1.56% |
| FastMM5 | ab 请求/秒 | 40,577.990 | 40,608.080 | +0.07% |
| FastMM5 | Bombardier P99 ms | 1.957 | 1.959 | +0.10% |
| FastMM5 | 服务端 CPU μs/成功请求 | 114.045 | 116.792 | +2.41% |

噪声必须与点估计一起看：

- 默认 RTL 的同版本 A/A 吞吐变化范围为 -7.21%～+1.26%，噪声较大。A/B 五对均下降，逐对为 -8.77%～-3.90%，中位下降 5.85%；各组中位数之比为 -7.75%。可报告本次观测到下降，但不能把 7.75% 当成固定或高精度损失。
- FastMM5 的 A/A 范围为 -0.36%～+0.05%；A/B 五对为 -2.37%～+0.45%，三对下降、两对上升，逐对中位下降 0.71%。各组中位数之比为 -1.56%，属于小幅、仍有波动的整体影响；ab 基本持平，P99 也基本持平。
- 1000 并发时，Before + 默认 RTL 的第一个样本已有 7725 次连接拒绝，已排除。统一降低至 128 并发后重新做两组 A/A、A/B；没有改变生产 backlog，不把失败尝试当成功吞吐。原始失败 JSON 保留在 `bin/perf199-20261028/http/rtl/aa/0-a1.bomb.json`。

## 解释与后续定位

- 可以确认新增成本不只来自保存 raw：不生成 raw 的字符串 Decode 也慢约 40%～48%；ASCII 出站分配次数基本不变，但耗时增加约 76%～109%。
- 本轮没有做调用栈采样或逐项消融，不能把总回退全部归给某一处。优先候选是 FPC 下的协议字段名判定、逐字段 GetString/记录复制，以及共用扫描器的逐字符读取和出站完整性扫描。
- 请求目标没有 query 时，RawPathAndQuery 与 RawPath 对同一字节区间分别调用 GetString，是可进一步单独验证的重复工作；尚未修改。
- 这些功能包含原始字节持有、严格失败、控制字段校验和 UTF-8 输出等合同差异。后续优化应保留正确性，不以删除校验或原始数据来制造性能收益。
- 未测 FPC/Win32 的端到端服务吞吐、TLS、Linux/macOS/ARM、真实业务路由、复杂 POST 正文或读取 RawRequestHeader 副本的业务成本；不能从本轮数字推导这些场景。


- `PERFORMANCE_RESULTS.json`：可随代码保存的结果摘要。

- `bin/perf199-20261028/micro.json`：全部 A/A、A/B、语义判定和分配样本。
- `bin/perf199-20261028/memory.json`：存活对象内存三轮测量。
- `bin/perf199-20261028/http-c128.json` 与 `http/*/*-c128/`：全部成功样本、ab/Bombardier 原始输出和服务日志。
- 各 `before/after/<target>/build.json` 为已完成计时批次的构建记录（新复跑名为 `HeaderBench-build.json`）；内存批次使用 `HeaderMemoryBench-build.json`。微基准代码中 `raw_value_bytes` 只在 wire/request 模式采样，其他模式的 0 不作为原始值持有量结论。

实际使用的计时/吞吐驱动与两份 Pascal 基准源码另存于 `bin/perf199-20261028/harness/`，其哈希已与测量记录核对。
